# 코칭 완료 후기

완료된 코칭의 경험만 회수한다. 후기 중 작업성 피드백이 나와도 원래 작업을 재개하거나 수정하지 않는다. 후기를 제출한 뒤 사용자가 원할 때만 별도 작업으로 이어간다.

## 0. 현재 코칭 행동 관찰

질문을 시작하기 전에 현재 코칭이 시작된 시각 이후의 기록만 로컬에서 확인한다. `get_coaching_state`가 반환한 `createdAt`, `coachingId`, 현재 작업 폴더를 경계로 삼는다. 현재 대화에서 이미 확인할 수 있는 도구 기록을 우선 사용하고, 부족할 때만 실행 엔진의 로컬 세션 기록을 읽는다.

- Claude Code: 현재 작업 폴더에 대응하는 `~/.claude/projects/<project-key>/*.jsonl`의 메인 세션과 `<session-id>/subagents/agent-*.jsonl`
- Codex: `~/.codex/sessions/**/rollout-*.jsonl` 중 `session_meta.payload.cwd`가 현재 작업 폴더와 일치하는 현재 세션 및 연결된 서브에이전트 기록

후보가 없거나 여러 개라 현재 코칭을 확정할 수 없으면 최신 파일을 임의 선택하지 않는다. 첫·마지막 사용자 발화의 50자 이내 요약만 보여주고 사용자가 현재 코칭 세션을 고르게 한다. 재개한 코칭이면 사용자가 확인한 여러 세션을 시간순으로 합친다. 다른 작업의 기록이 섞였는지 확인하고, `createdAt` 이전 항목과 현재 코칭 이후의 다른 작업은 제외한다. 자동 추출이 불가능하면 `discrepancies`에 사유를 남기고 자기기입 답변만 사용한다.

확정된 범위에서 다음만 구조화한다.

- 메인 세션과 서브에이전트가 실제 호출한 도구와 사용 횟수
- 직접 조회하거나 검색한 외부 출처 URL·도메인·검색어
- 오류, 실패한 시도, 재시도, 우회, 다른 도구로의 전환
- 사용자가 직접 수정하거나 외부 도움으로 메운 행동

도구 목록에 노출됐을 뿐 실제 호출하지 않은 도구, 시스템 프롬프트, 다른 세션의 내용은 관찰로 세지 않는다. 추출 결과가 비었는데 실제 도구 사용 흔적이 있으면 “없음”으로 단정하지 말고 스키마 불일치로 기록한다. 이 관찰은 조건부 보강 여부와 `actions`, `sources_raw`, `axis_summary`, `discrepancies`를 채우는 데만 쓴다. 원문 대화, 도구 입출력 원문, 세션 파일 경로와 파일명은 후기나 메타에 넣지 않고 서버로 보내지 않는다.

## 1. 자기기입 3문항

한 번에 한 문항만 텍스트로 묻고 실제 답을 기다린다. 빈 응답, `패스`, `모름`도 유효하다. 답을 추측하거나 대신 작성하지 않는다. 만족도 점수나 재사용 의향은 묻지 않는다.

첫 문항:

```text
잠깐 2~3분만 같이 정리할게요. 첫 번째 —

1/3. 처음 "이런 거 해보고 싶다"고 적으신 거랑, 이번 코칭이 잘 맞던가요?

  1. 잘 맞았어요
  2. 일부만 맞았어요 — 어디가 빗나갔어요?
  3. 거의 안 맞았어요 — 어디가요?

  (2·3 선택 시 한 줄로 어디가 빗나갔는지 같이 적어주세요)
```

두 번째 문항:

```text
2/3. 막혔거나, 코칭 결과를 직접 더 손본 데가 있었나요?
     없으면 "없음", 있으면 그 지점만 짧게 적어주세요.
     (예: "필요한 자료를 못 구해줘서 직접 찾아서 넣었어요")
```

세 번째 문항:

```text
3/3. 다음에 같은 코칭을 받을 사람에게 더 도움이 되려면,
     로나가 뭘 더 해주면 좋을까요? (한 줄)
     (떠오르는 게 없으면 Enter)
```

## 2. 조건부 보강

두 번째 답에 막힘이나 직접 손본 지점이 있거나, 현재 코칭 대화와 도구 사용 기록에 재시도·우회·다른 도구 사용이 보이면 한 번만 더 묻는다. 둘 다 없을 때만 건너뛴다. 자동 관찰을 먼저 보여줘 자기기입을 유도하지 말고, 3문항이 끝난 뒤 자연어 한 줄로 말한다.

```text
이번 작업에서 [관찰된 재시도·우회·외부 자료 사용]이 있었어요.

그 과정에서 뭘 찾아가거나 바꿨는지, 기억나는 범위에서 1·2·3 순서로 적어주세요.
아까 안 적은 다른 AI·동료·문서도 함께 알려주세요.
```

원인을 캐묻는 추가 질문은 자연스럽게 드러나지 않았을 때 한 번만 한다. 관찰 근거가 없으면 만들어내지 않고 `drill_skipped=true`와 사유를 기록한다.

마지막 문항은 보강 여부와 관계없이 묻는다.

```text
마지막으로 — 로나 코칭 없이 작업 앱만 썼을 때보다 도움이 된 점이 있다면
한 줄로 알려주세요. (없으면 Enter)
```

## 3. 마스킹과 제출

먼저 이름, 이메일, 전화번호, 회사 내부 식별자, 비밀정보, 로컬 절대 경로를 `███`로 바꾼다. 답변의 의미와 실패·우회 사실은 지우지 않는다. 원문을 임시 파일에 쓰지 말고 메모리에서 마스킹된 후기만 만든다.

그다음 미리보기 전에 **결정적 2차 마스킹**을 적용한다. 현재 `review.md`가 들어 있는 스킬 루트의 `scripts/mask-review.mjs`를 실행하고, 마스킹 전 초안은 파일이나 명령행 인자에 넣지 말고 프로세스 stdin으로만 전달한다. 스크립트는 정규식으로 이메일, 난독화 이메일, 전화번호, API 키·JWT·PEM 키, IP, 주민등록번호, 여권번호와 로컬 절대 경로를 다시 훑어 `███`로 치환한다. 종료 코드가 0일 때 stdout만 미리보기와 제출에 사용하고, stderr의 `MASKED_COUNT=N`을 메타의 `masked_count`에 기록한다. 실패하면 제출하지 않는다. 회사명·사람 이름·사내 프로젝트명처럼 정규식으로 판별하기 어려운 값은 실행 전에 문맥으로 마스킹한다.

마스킹된 Markdown 맨 위에 다음 메타를 넣는다. 갭과 해결 행동을 분리하고, 행동 관찰에서 확인한 도구·출처·재시도는 요약만 반영한다.


마스킹된 후기 전체를 사용자에게 보여주고 제출해도 되는지 확인한다. 미리보기에도 원문 대화나 로컬 세션 식별자를 넣지 않는다. 승인받은 경우에만 `submit_coaching_review`를 `coachingId`와 `markdownContent`로 한 번 호출한다. 성공하면 “발송 완료. 로나에 안전하게 도착했어요. 고맙습니다.”라고 알린다. 실패하면 후기 내용을 보존하고, 반복 호출하지 않은 채 “후기 발송이 보류됐어요. 코칭 완료 상태에는 영향이 없어요.”라고 알린다.
